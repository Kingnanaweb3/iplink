Attestcoin Protocol Integration

IPlink lets creators raise capital against real, future royalty income. This document explains — with real transaction hashes, not diagrams alone — exactly how Attestcoin Protocol verification drives that financing, trustlessly.

Overview

Our Campaign contract's verification entry point, execute(), has no access control — anyone can call it. That's intentional. Trust doesn't come from who submits a proof, it comes from the proof itself being checked on-chain by Creditcoin's Block Prover precompile before a single line of business logic runs.

  • No centralized oracle operator decides what's true
  • Verification and business logic execute synchronously, in one transaction
  • Replay protection prevents the same proof being submitted twice
  • Only events from our registered RoyaltyPayer source contract are accepted

Why Attestcoin, not a bridge or an oracle

IPlink needs to know, with certainty, that a real royalty payment happened on a source chain — before releasing capital or paying an investor. Three approaches were possible; only one avoids reintroducing a trusted middleman.

Rejected

A token bridge

Bridges move assets, not facts. We don't need to move a token across chains — we need to prove an event happened where it happened. Using a bridge here would be the wrong tool solving an adjacent problem.

Rejected

A centralized oracle

An oracle operator reporting "yes, this payment happened" is exactly the single point of trust and failure the hackathon's own Attestcoin brief is designed to eliminate. It would undercut the entire pitch.

Used

Attestcoin Protocol

Proves transaction inclusion on the source chain using Merkle and continuity proofs, verified natively on Creditcoin in about one block. No operator, no async wait, no intermediate state.

function _processAndEmitEvent(uint8, bytes32, bytes memory encodedTransaction) internal override {
    uint8 txType = EvmV1Decoder.getTransactionType(encodedTransaction);
    require(EvmV1Decoder.isValidTransactionType(txType), "Unsupported transaction type");

    receipt = EvmV1Decoder.decodeReceiptFields(encodedTransaction);
    require(receipt.receiptStatus == 1, "Source transaction did not succeed");

    logs = EvmV1Decoder.getLogsByEventSignature(receipt, ROYALTY_PAID_EVENT_SIGNATURE);
    require(logs.length > 0, "No RoyaltyPaid event found");
    require(logs[0].address_ == royaltyPayer, "Event not from registered RoyaltyPayer");

    _recordVerifiedRevenue(amount);
}
function execute(...) external returns (bool success) {
    bytes32 queryId = _computeQueryId(chainKey, blockHeight, merkleRoot, siblings);
    require(!processedQueries[queryId], "Query already processed");

    bool verified = _verifyProof(
        chainKey, blockHeight, encodedTransaction,
        merkleRoot, siblings, lowerEndpointDigest, continuityRoots
    );
    require(verified, "Proof of inclusion verification failed");

    processedQueries[queryId] = true;
    _processAndEmitEvent(action, queryId, encodedTransaction);
    return true;
}

What this is, and isn't, doing

Precision here matters more than a polished story. Two things are worth stating plainly.

Verification proves a fact. It doesn't move money.

Attestcoin confirms a payment happened on the source chain — it does not teleport funds. Payout capital on Creditcoin is deposited separately by the creator. This is correct cross-chain design, not a missing feature: mixing "proof of fact" with "custody of funds" is exactly the kind of coupling that makes bridges risky.

Revenue units are currently a 1:1 numeric mapping.

The wei-denominated value from the source-chain event is used directly as the accounting number for the revenue split, without a unit-conversion or price-oracle step. Correct for a same-scale testnet demo; a production version would need an explicit settlement-asset design rather than assuming source-chain value and Creditcoin value are numerically interchangeable.

Security review and fixes

We audited our own contracts and found ten issues, several severe. All of them are addressed in the deployed version below, and each fix has a test in the repository. Listing them here rather than quietly patching them is deliberate — the point of this project is verifiable claims.

Fixed — share token transfer drain

Payout accounting keys off a per-holder checkpoint. Transferring shares to a fresh address reset that checkpoint to zero, letting the recipient re-claim the entire cumulative revenue history — repeatedly, draining other investors' funds. Share tokens are now non-transferable. Secondary trading requires checkpointed balances and is out of scope for this version.

Fixed — capital release over-withdrawal

releaseCapital() withdrew the contract's entire balance with no once-only guard, so a creator could call it again after payout funds were deposited and take those too. It now transfers a fixed amount, once, and reverts on any repeat call.

Fixed — cross-campaign proof replay

Replay protection was per-campaign, but the only ownership check was the creator address. Two campaigns sharing a creator could both consume a proof of the same single payment. The RoyaltyPaid event now carries the campaign address, and a campaign rejects any proof naming a different one.

Fixed — investing twice erased earnings

A second investment reset the holder's checkpoint, silently discarding everything accrued from the first. Accrued value is now settled into a separate owed balance before any position change.

Fixed — no refund path, false completion, bricking, self-investment, dust

Campaigns now have a funding deadline with a refund() for unfilled raises. Completion status is gated on the contract's actual balance via isFullyBacked(), not accounting alone. Oversized payments are capped at the remaining amount owed rather than reverting permanently. Creators cannot invest in their own campaigns. Division remainders carry forward instead of being lost.

The reserve, and what it does not solve

40% of every raise stays in the contract to cover investor payouts, so investors are not wholly dependent on a creator voluntarily depositing funds later.

Creator abandonment is bounded, not prevented

A creator can still take their 60%, never verify any revenue, and walk away. Investors would recover at most the reserve. No contract can compel someone to earn money — the real answers are tranched release tied to verified revenue milestones, or legal recourse, and neither belongs in a testnet build. This is unsecured revenue-share financing and the risk is real.

Revenue origination is restricted, not verified

Only whitelisted addresses can originate a payment on RoyaltyPayer, which stops third parties fabricating revenue. A whitelisted creator paying themselves still would. The genuine fix is pointing at a distributor's real payout contract, established during onboarding — not something that can be simulated on testnet.
